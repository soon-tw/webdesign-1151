為什麼是「計畫」，不是「成品」

課程進度：01 / 06　作業規格與方向本頁主題：計畫的價值

這份作業先看「想清楚了沒有」，不是先看「會不會寫」。

  • 計畫是導航：範圍先定下來，才不會做到一半迷路。
  • 期末實作報告要用同一份計畫當第一章，兩份作業接得起來。
  • 能把想法講清楚，是工程師最被低估的能力。
  • 寫計畫的過程，通常會發現原本的題目太大。
  • 有計畫，才看得出來「哪裡還沒想清楚」。
  • 這份計畫不需要漂亮，需要具體。
這頁記住：計畫＝把「想做什麼」講到別人聽得懂。

什麼是 MVP

課程進度：01 / 06　作業規格與方向本頁主題：MVP

MVP 是 Minimum Viable Product，最小可行產品。

  • 能驗證想法的最小範圍，不是「功能少一點的完整版」。
  • 砍到只剩：一個使用者、一個情境、一條流程。
  • 功能分三格：Must 一定要、Should 有更好、Won't 這次不做。
  • 做得完，永遠比做得多重要。

區塊 01｜問題與痛點

課程進度：02 / 06　AI Agent Plan 架構內容框架本頁主題：問題定義

這個作品解決的是誰的什麼麻煩？

  • 一句話寫完：「＿＿的人，每次要＿＿，都得＿＿。」
  • 要有具體場景，不要寫「提升效率」這種空話。
  • 附上證據：自己的經驗、觀察，或問 1–3 個同學。
  • 寫不出來，代表題目還沒想清楚。

句型卡

「進修部的同學，每次要賣掉上學期的教科書，都得在群組裡一張一張翻訊息。」

反例：「打造一個賦能學習生態的一站式平台。」——沒有畫面，也沒有使用者。

這頁記住：痛點要具體到可以想像那個畫面。

11/39

區塊 02｜目標使用者與使用情境

課程進度：02 / 06　AI Agent Plan 架構內容框架本頁主題：使用者

先鎖定一個人，不要寫「所有人」。

  • 使用者側寫：身分、使用裝置、使用時間、熟悉度。
  • 主要情境（User Story）：作為＿＿，我想要＿＿，才能＿＿。
  • 寫 2–3 條就好；寫到 5 條以上，代表範圍沒收斂。
  • 標出「最重要的那一個情境」，那就是 MVP 的核心。

使用者側寫範例

身分　進修部在職生，晚上上課
裝置　手機為主，偶爾用筆電
時間　下課後 10 分鐘內
熟悉度　會用 LINE，不熟購物網站

把這四行寫進計畫，第 03 區塊的功能就不會亂長。

這頁記住：使用者寫得越具體，功能就越不會亂長。

區塊 03｜MVP 功能範圍

課程進度：02 / 06　AI Agent Plan 架構內容框架本頁主題：功能範圍

把功能分成三格，並且勇敢寫下「這次不做」。

  • Must（1–3 項）：沒有它，這個作品就不成立。
  • Should（1–2 項）：有時間再做，不要當成承諾。
  • Won't：明確寫出這次不做的功能，範圍才守得住。
  • 每一項功能都要連回第 02 區塊的使用者情境。
圖解 B｜MVP 功能範圍的三格
這頁記住：敢寫 Won't，計畫才有範圍。

區塊 04｜使用者流程與畫面規劃

課程進度：02 / 06　AI Agent Plan 架構內容框架本頁主題：流程與畫面

從打開網頁到完成任務，畫出一條路。

  • 手繪線框圖就好：紙上畫完拍照貼上，不用漂亮。
  • 每個畫面標出區塊位置：標題、清單、按鈕在哪。
  • 畫面之間畫箭頭：哪一顆按鈕會去哪一頁。
  • 標出「資料從哪來、顯示在哪」。
  • 建議 3–5 個畫面：首頁／清單／詳情／表單／結果。

一條流程的範例

首頁 → 書目清單 → 書籍詳情 → 我要刊登（表單）→ 送出成功

每個箭頭都要說得出「按了哪一顆按鈕」。

畫不出來，代表功能切得太粗或太細。

這頁記住：一張手繪流程圖，勝過一千字描述。

區塊 06｜資料來源與 API

課程進度：02 / 06　AI Agent Plan 架構內容框架本頁主題：資料與 API

資料從哪來？先確認它真的拿得到。

  • 三種來源：自己寫的假資料、公開 API、自己整理的表。
  • 用公開 API 就要寫出：網址、欄位、授權、更新頻率。
  • 先做「資料快照」：課前抓一份存下來，API 掛掉也能上課。
  • 沒有 API 就用假資料模擬（CH6 練習 6 示範過）。
  • 資料有版權或個資疑慮，就換一個題目。

資料清單要寫什麼

來源　臺中市 YouBike 公開資料
網址　（貼上實際網址）
欄位　站點名稱、可借車輛數、可還空位數
授權　政府資料開放授權條款第 1 版
更新　每 1 分鐘；快照日期 2026-11-05

沒有這一頁，期末最常見的失敗就是「資料拿不到」。

這頁記住：資料拿不到，再漂亮的計畫都做不出來。

區塊 08｜風險與備案

課程進度：02 / 06　AI Agent Plan 架構內容框架本頁主題：風險

每一條風險，都要配一句「如果發生，我就＿＿」。

  • 常見風險：API 掛掉、套件版本不合、時間不夠、臨時有事。
  • 備案要能在 30 分鐘內啟動，否則不算備案。
  • 標出「最可能發生」和「最嚴重」的各一條。
  • 時程裡要留一格緩衝，它通常會被風險吃掉。

風險與備案範例

風險　上課當天 API 掛掉

備案　改用課前抓好的資料快照，並在畫面標示資料時間

每一條風險都長這個樣子：一句風險，一句「我就＿＿」。

這頁記住：沒有備案的風險，就是一定會爆的那一顆。

區塊 09｜驗收標準

課程進度：02 / 06　AI Agent Plan 架構內容框架本頁主題：驗收標準

用「可觀察的句子」寫完成定義。

  • 句型：「當我＿＿，我應該看到＿＿。」
  • 至少涵蓋四種狀態：載入中／成功／錯誤／沒有資料。
  • 寫下「最小可交付」：其他都沒做，這一條也要成立。
  • 驗收句寫得出來，就代表知道要做什麼。

驗收句範例

當我打開首頁，我應該看到書籍清單（至少 6 筆）。

當我搜尋「微積分」，我應該只看到書名含「微積分」的書。

當資料還沒回來，我應該看到「載入中」而不是空白。

當查不到資料，我應該看到「沒有符合的書」而不是壞掉。

這頁記住：寫得出驗收句，就代表知道要做什麼。

區塊 10｜把框架問清楚

課程進度：02 / 06　AI Agent Plan 架構內容框架本頁主題：協作紀錄

逐區塊自問自答，把還沒想清楚的地方逼出來。

  • 先自己寫三行草稿，再逐區塊補齊。
  • 給出具體內容：使用者、情境、功能、技術限制。
  • 請人反問問題，而不是直接給答案。
  • 產出後逐條刪改：刪空話、補上自己的現場細節。

自問清單

我的題目是＿＿，使用者是＿＿。

針對「問題、使用者、範圍、風險、驗收」五個面向，各寫下三個問題。

逐題回答；回答不出來的，就是還沒想清楚的地方。

最後列出「還沒回答的問題」，回過頭改計畫。

這頁記住：問題問得越具體，計畫就越站得住。

簡報呈現的重點

課程進度：02 / 06　AI Agent Plan 架構內容框架本頁主題：簡報呈現

這份作業交的是簡報，不是文件；讓人看得下去，本身也是評分項目。

  • 一頁只講一件事，標題就是那一頁的重點。
  • 條列不超過五條，超過就拆成兩頁。
  • 流程圖手繪就可以，看得懂比漂亮重要。
  • 把 Won't 與風險具體寫出來，那才是專業的地方。

值得做

  • 一頁只講一件事
  • 驗收句寫成可觀察的句子
  • 手繪流程圖也可以
  • 把 Won't 具體寫出來

盡量避免

  • 每頁都塞滿文字
  • 功能清單沒有分級
  • 只寫技術名詞，沒寫理由
  • 整份都沒有圖，全是條列
這頁記住：一頁一件事，比一頁塞十件事好。

選題的三個判準

課程進度：04 / 06　選題技能方向：Frontend Roadmap本頁主題：選題判準

三個判準，過不了就換題目——不是打擊，是省下兩週。

  • 可做：用學過的技術＋一份拿得到的資料，兩週內做得完。
  • 可驗：寫得出「當我＿＿，我應該看到＿＿」的驗收句。
  • 有感覺：自己會想用它——撐過期末靠的是興趣。
  • 反例：「整合金流的電商平台」太大，先做「一個商品清單」。
  • 題目越小越容易做完整；做得完整，分數越高。
這頁記住：小題目做到完整，勝過大題目做一半。
